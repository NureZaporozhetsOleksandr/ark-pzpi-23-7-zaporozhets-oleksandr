     5.2 Хід роботи
     5.2.1 Використання SQLite у розгорнутій системі
     У якості системи зберігання даних у проєкті використовується SQLite — файлова реляційна база даних, яка не потребує окремого серверного процесу. Дані зберігаються у файлі з розширенням .db, а доступ до БД здійснюється безпосередньо з серверної частини Node.js через бібліотеку sqlite3.
     Підключення до SQLite реалізовано у модулі доступу до БД (db-модуль), де формується шлях до файлу бази даних і виконується відкриття з’єднання. Після ініціалізації додатково вмикається підтримка зовнішніх ключів командою PRAGMA foreign_keys = ON, що забезпечує коректну роботу зв’язків між таблицями та запобігає порушенню цілісності даних.
     Під час запуску сервер виводить у логи повідомлення про успішне підключення до SQLite із зазначенням повного шляху до файлу .db. Це використовується як підтвердження, що база даних доступна в середовищі виконання після розгортання.

Рис. 5.1 – Лог запуску сервера з повідомленням про підключення до SQLite з Render
     Особливістю використання SQLite в хмарному середовищі є те, що БД є файловою, тобто залежить від файлової системи середовища розгортання. Для навчального проєкту це допустимо, однак важливо враховувати, що при перевстановленні/перезапуску середовища або повторних деплоях дані можуть бути втрачені, якщо файл бази не зберігається у постійному сховищі. Тому для довготривалого збереження даних у хмарі доцільно використовувати або персистентний диск/том, або перейти на клієнт-серверну СУБД (MySQL/PostgreSQL). У межах даної лабораторної роботи SQLite використовується як спрощене та зручне рішення для демонстрації працездатності серверної частини та бізнес-логіки.

Рис. 5.3 – Логи деплою та запуск сервера
     Для коректного запуску застосунку в хмарі було враховано вимоги до середовища виконання: сервер повинен слухати порт, який задається змінною середовища платформи. Тому у коді використовується process.env.PORT як основний порт запуску, а локальне значення використовується як запасне.
     Також для коректної роботи Swagger UI у продакшн-середовищі налаштовано параметр servers у Swagger-специфікації. Замість прив’язки до http://localhost:3000 використано значення '/', що дозволяє Swagger автоматично виконувати запити в межах поточного домену Render. Це усуває проблему “Failed to fetch” та забезпечує працездатність інтерактивного тестування endpoint-ів у браузері.
5.2.3 IoT-модуль (симуляція у Wokwi) та інтеграція з бекендом
     Для демонстрації взаємодії програмної системи з IoT-пристроєм було використано симулятор Wokwi, інтегрований у середовище Visual Studio Code. Wokwi дозволяє емулювати роботу мікроконтролера та периферії без фізичного обладнання, що є зручним для навчального проєкту та швидкої перевірки логіки збору даних.
     У межах роботи IoT-пристрій реалізовано на базі ESP32 (симуляція). Після запуску прошивка виконує ініціалізацію компонентів, підключається до Wi-Fi мережі, після чого формує телеметрію з поточних показників датчиків/параметрів. Далі дані періодично відправляються на серверну частину HiveTrack через HTTP-запит (формат REST). Передача виконується у форматі JSON, що забезпечує сумісність із серверним API та спрощує подальшу обробку й збереження.
Алгоритм роботи IoT-модуля можна описати так:
1. старт пристрою та ініціалізація (ESP32 + бібліотеки);
2. підключення до Wi-Fi за вказаними параметрами;
3. формування структури даних телеметрії;
4. відправка телеметрії на ендпоінт бекенду за допомогою HTTP POST;
5. отримання відповіді сервера (код статусу / підтвердження прийому) та повтор циклу через заданий інтервал.
   Інтеграція з бекендом реалізована таким чином, що у коді IoT-модуля задається адреса серверного API (URL Render-сервісу) та маршрут, який приймає телеметрію. Таким чином, симуляція у Wokwi підтверджує не лише коректність формування даних на боці “пристрою”, а й працездатність мережевої взаємодії із розгорнутим бекендом у хмарі.
У процесі демонстрації працездатність інтеграції підтверджується двома способами:
• на боці IoT-модуля видно успішну відправку HTTP-запиту та статус відповіді;
• на боці бекенду у логах Render або через Swagger можна підтвердити, що запит був отриманий і оброблений (або збережений, якщо реалізовано запис у БД).
