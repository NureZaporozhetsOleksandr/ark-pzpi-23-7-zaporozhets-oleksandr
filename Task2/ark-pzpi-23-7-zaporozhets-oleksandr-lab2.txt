1 БУДОВА ПРОГРАМНОЇ СИСТЕМИ
1.1 Архітектурні рішення для серверної частини системи
     Програмна система для моніторингу праці співробітників реалізується як веб-застосунок із клієнт-серверною архітектурою. Клієнтська частина працює в звичайному браузері, а серверна — на окремому застосунковому сервері, що взаємодіє з базою даних. Такий підхід відповідає вимогам до доступності, простоти розгортання й можливості подальшого масштабування системи. 
     Серверна частина побудована на платформі Node.js з використанням фреймворка Express.js. Вона виконує такі основні функції: обробка HTTP/HTTPS-запитів від клієнта, реалізація бізнес-логіки обліку робочого часу, перевірка прав доступу користувачів залежно від ролі (співробітник/адміністратор), формування звітів та логування всіх подій у системі. Через REST-інтерфейс сервер надає набір кінцевих точок для роботи з користувачами, відмітками часу, робочим графіком і журналом змін. 
     Для зберігання даних використовується реляційна СУБД SQLite. Вона забезпечує зберігання всієї бази у вигляді одного файлу, що спрощує розгортання системи в умовах обмежених ресурсів та відповідає підходу до створення MVP-рішення для невеликих організацій. У базі зберігаються облікові записи співробітників, їхні ролі, робочі графіки, відмітки початку й завершення роботи, записи про перерви, відрядження, лікарняні та відпустки, а також дані журналу змін. 
     Клієнтська частина реалізована як веб-інтерфейс на основі React з використанням HTML, CSS та JavaScript. Вона забезпечує мінімалістичний, інтуїтивно зрозумілий інтерфейс для швидкого внесення відміток, перегляду особистої історії, формування звітів і виконання адміністративних операцій. Оновлення даних на сторінці виконується через асинхронні запити до REST API, що дозволяє працювати без повного перезавантаження сторінки й робить взаємодію з системою комфортною для користувача. 
     Передбачено використання HTTPS для шифрування всього трафіку між клієнтом і сервером. Авторизація здійснюється за логіном і паролем, паролі зберігаються в зашифрованому вигляді (хешування за допомогою сучасних алгоритмів, таких як bcrypt або Argon2). Для підтримки сесій застосовується токен-автентифікація (JWT), а рольова модель забезпечує розмежування прав між співробітниками й адміністраторами. Регулярне резервне копіювання файлу бази даних дозволяє відновити систему у разі збоїв або помилок користувачів.

1.2 Моделі, що використовуються в системі
     Архітектура системи ґрунтується на наборі доменних моделей, які відображають ключові сутності предметної області обліку робочого часу співробітників. Основні з них:
     Модель User (Користувач)
     Центральна сутність системи, яка представляє окремого співробітника або адміністратора. Містить дані про ім’я, логін, електронну адресу, хеш пароля, роль у системі, а також стан облікового запису. Один користувач може мати багато пов’язаних записів робочого часу та подій відсутності. 
     Модель Role (Роль)
     Визначає тип доступу користувача: «співробітник» або «адміністратор». Співробітник може створювати відмітки власного робочого часу й переглядати свою статистику; адміністратор додатково має доступ до керування користувачами, робочими графіками, перегляду звітів по всій організації та корекції помилкових записів. У реалізації роль може зберігатися як окреме поле в моделі User або як пов’язана довідкова таблиця. 
     Модель WorkSchedule (Робочий графік)
     Описує нормативний графік роботи співробітників: час початку та завершення робочого дня, допустимі перерви, тривалість зміни, вихідні дні тощо. Графік може задаватися як для всієї організації, так і для окремих співробітників або підрозділів. На основі цієї моделі система визначає запізнення, понаднормові години та коректність внесених відміток. 
     Модель TimeEntry (Відмітка часу)
     Фіксує конкретну подію в робочому дні співробітника: прихід, вихід, початок/кінець перерви, відрядження, лікарняний або відпустку. Кожен запис містить тип події, точний час, користувача, до якого він належить, та, за потреби, коментар. На основі набору відміток система автоматично розраховує відпрацьовані години за день, тиждень або місяць, а також визначає запізнення та понаднормову роботу. 
     Модель AbsenceRecord (Запис відсутності)
     Використовується для зберігання більш довготривалих періодів відсутності співробітника: відпустки, лікарняні, відрядження, навчання тощо. Містить дати початку й завершення, тип відсутності та посилання на користувача. Ця модель дозволяє коректно формувати звіти за період, виключаючи дні офіційної відсутності з розрахунку робочих годин. 
     Модель Report (Звіт)
     Логічна модель, яка описує агреговані дані для вивантаження й відображення керівництву або HR: загальна кількість відпрацьованих годин, кількість запізнень, понаднормових годин, перерв тощо. Звіти будуються на основі TimeEntry та WorkSchedule і можуть формуватися за день, тиждень, місяць або довільний період, з можливістю експорту у табличні формати. 
     Модель ChangeLog (Журнал змін)
     Призначена для фіксації всіх змін у критично важливих даних: хто і коли відредагував відмітку часу, змінив графік роботи чи дані користувача. Це дозволяє відстежувати помилки, запобігати зловживанням та забезпечувати прозорість у роботі системи. 
     У сукупності ці моделі утворюють цілісну структуру, у центрі якої знаходиться користувач, а всі інші сутності — записи часу, графіки, періоди відсутності, звіти та журнал змін — описують різні аспекти його робочої діяльності. Така побудова забезпечує можливість гнучкого аналізу даних і подальшого розширення функціоналу системи.

2.2 Опис діаграми
     На діаграмі прецедентів показано, як різні типи користувачів взаємодіють із серверною частиною системи через набір функцій, визначених у документі бачення рішення. 
Актор «Співробітник»
     Співробітник є основним користувачем системи, який щодня взаємодіє з нею для фіксації свого робочого часу. Для нього передбачені такі прецеденти:
• Зареєструватися / Увійти в систему – автентифікація за логіном і паролем.
• Зробити відмітку початку робочого дня – фіксація часу приходу на роботу.
• Зробити відмітку завершення робочого дня – фіксація часу виходу.
• Зробити відмітку перерви – початок та кінець перерви впродовж дня.
• Зробити відмітку відрядження / лікарняного / відпустки – внесення подій тривалої відсутності.
• Переглянути власну історію відміток – доступ до журналу своєї активності за день/тиждень/місяць.
• Переглянути особистий звіт – перегляд автоматично сформованої статистики відпрацьованих годин, запізнень та понаднормових. 
     Ці прецеденти реалізують базові потреби співробітника: просту фіксацію часу та доступ до власних даних без зайвих дій. 
Актор «Адміністратор / HR»
     Адміністратор (або HR-фахівець) відповідає за налаштування системи, керування обліковими записами та контроль дисципліни. На діаграмі для нього передбачено такі прецеденти:
• Увійти як адміністратор – авторизація з розширеними правами.
• Керувати співробітниками – додавання нових користувачів, редагування профілів, деактивація облікових записів.
• Налаштувати робочий графік – визначення стандартного робочого дня, вихідних, тривалості перерв. 
• Переглядати журнали активності – доступ до історії відміток усіх співробітників.
• Формувати звіти – побудова зведених таблиць по відпрацьованих годинах, запізненнях і понаднормовій роботі за вибраний період.
• Експортувати звіти – вивантаження даних у CSV/PDF/Excel для подальшої обробки в бухгалтерії чи HR-системах. 
• Переглядати журнал змін – контроль за усіма правками у даних (зміни відміток, корекція графіків тощо).
     Таким чином, адміністратор реалізує функції керування користувачами та відповідає за цілісність і коректність даних у системі.
Актор «Керівник»
     Керівник (менеджер підрозділу або власник бізнесу) не змінює дані напряму, але зацікавлений у прозорій аналітиці. Для нього передбачено:
• Переглянути зведені звіти по підлеглих – отримання агрегованої інформації щодо відпрацьованого часу, запізнень та відсутностей по відділу чи окремих працівниках.
• Аналізувати дисципліну й навантаження – використання сформованих звітів для ухвалення управлінських рішень. 
     У UML-діаграмі ці прецеденти можуть бути пов’язані відношеннями «include» з базовими сценаріями формування звітів, які реалізує серверна частина.

3.1 Опис ER-діаграми
     ER-діаграма відображає логічну структуру бази даних системи моніторингу праці співробітників. У її центрі знаходиться сутність Users, яка представляє всіх користувачів системи — як співробітників, так і адміністраторів. Таблиця містить основні дані облікового запису: ПІБ, логін або електронну адресу, хеш пароля, роль та статус активності. Від цієї сутності відходить найбільша кількість зв’язків, оскільки саме співробітник є ключовим учасником робочих процесів, а адміністратор — центральною фігурою управління системою.
     З Users пов’язано кілька сутностей, що відображають різні аспекти робочої діяльності. Сутність TimeEntries містить усі відмітки часу, які фіксують події робочого дня: початок та завершення роботи, початок і кінець перерви, а також інші операції, пов’язані з обліком робочого часу. Зв’язок «один до багатьох» дозволяє одному співробітнику мати довільну кількість таких записів, що необхідно для формування детальної історії активності та точного обліку відпрацьованих годин.
     Ще однією важливою сутністю є AbsenceRecords, яка зберігає інформацію про періоди відсутності працівника: відпустки, лікарняні або відрядження. Вона також пов’язана з Users через відношення 1..N. Така структура дає змогу коректно враховувати неробочі дні та формувати точні звіти без вручну внесених коригувань.
     Сутність WorkSchedules відповідає за зберігання робочих графіків. Запис може бути прив’язаний або до конкретного користувача, або бути загальним (якщо UserId = null). Вона містить час початку та завершення робочого дня, тривалість перерви та дні тижня, у які співробітник працює. Така модель дозволяє системі автоматично визначати запізнення, понаднормову роботу та інші аномалії в поведінці працівників.
     Остання сутність — AuditLogs — використовується для прозорості й контролю всіх змін у системі. Вона фіксує хто, коли й які дані змінив, а також містить старі й нові значення сутності. Це дозволяє адміністраторам відстежувати підозрілі дії, відновлювати дані у разі помилок та забезпечує цілісність системи.
     Узагальнюючи, ER-діаграма описує добре структуровану модель даних, де головним ядром є користувач, а всі інші сутності представляють різні аспекти його робочої діяльності. Така побудова дозволяє технологічно коректно реалізувати облік часу, управління робочими графіками, контроль відсутностей і аудит змін, забезпечуючи надійний і масштабований фундамент для серверної частини системи.
     
4 БАЗА ДАНИХ ПРОГРАМНОЇ СИСТЕМИ
4.1 Таблиці бази даних
     База даних програмної системи для моніторингу праці співробітників побудована таким чином, щоб повністю підтримувати бізнес-функції, визначені у документі бачення: реєстрацію та авторизацію, відмітки початку й завершення роботи, облік перерв, відряджень, лікарняних та відпусток, а також формування звітів і логування змін. 
     Центральною таблицею є Users, яка зберігає інформацію про всіх користувачів системи: співробітників та адміністраторів. У ній містяться поля для ідентифікатора користувача, ПІБ, логіна або електронної пошти, хешу пароля, ролі (наприклад, Employee або Admin) та ознаки активності облікового запису. Саме ця таблиця використовується для автентифікації користувачів (Ф1) та розмежування їхніх прав доступу відповідно до ролей. 
     Таблиця TimeEntries відповідає за зберігання всіх відміток робочого часу (Ф2–Ф3): початку та завершення робочого дня, початку й кінця перерви, а також інших подій, пов’язаних з обліком часу. Кожний запис містить зовнішній ключ на користувача, тип події, час початку, час завершення (для інтервальних подій) і необов’язковий коментар. На основі цих даних система може автоматично підраховувати кількість відпрацьованих годин за день, тиждень або місяць (Ф5) та виявляти запізнення й понаднормову роботу (Ф6). 
     Для врахування довготривалих відсутностей створено таблицю AbsenceRecords. Вона зберігає періоди відряджень, відпусток та лікарняних (Ф3): тип відсутності, дату початку та завершення, а також посилання на відповідного користувача. Це дозволяє коректно формувати звіти та не вважати такі дні порушенням графіка чи невиходом на роботу. 
     Таблиця WorkSchedules використовується для зберігання робочих графіків (Ф7 – «керування робочим графіком»). Вона містить час початку та завершення робочого дня, тривалість перерви та перелік робочих днів тижня. Графік може бути глобальним для всіх співробітників або налаштованим для конкретного користувача через поле UserId. На основі цієї таблиці система порівнює фактичні відмітки з нормативним графіком, що потрібно для автоматичного виявлення запізнень і понаднормових годин. 
     Для забезпечення прозорості роботи системи та можливості аудиту змін використовується таблиця AuditLogs (Ф10 – логування всіх змін та подій системи). У ній зберігаються записи про те, хто, коли і яку дію виконав: ім’я сутності, ідентифікатор зміненого запису, тип операції, час події, а також (за потреби) старі й нові значення. Ці дані дозволяють відстежувати всі критичні зміни та в разі потреби відновлювати правильний стан системи. 
     У сукупності дані таблиці формують цілісну модель: користувач (Users) має один або декілька робочих графіків (WorkSchedules), створює велику кількість відміток часу (TimeEntries), може мати періоди відсутності (AbsenceRecords), а всі важливі дії фіксуються в журналі подій (AuditLogs). 
     
5 ДІАГРАМА СТРУКТУРИ БД
5.1 Діаграма бази даних
     
     На діаграмі структури бази даних (рисунок 5.1) зображено фізичну схему БД програмної системи моніторингу праці співробітників. Центральною таблицею є Users, яка містить облікові записи всіх користувачів системи. У ній зберігаються такі основні поля, як Id (первинний ключ), повне ім’я користувача (FullName), логін (Login), електронна пошта (Email), хеш пароля (PasswordHash), роль (Role) та ознака активності (IsActive). Саме до цієї таблиці через зовнішні ключі підключені всі інші сутності, тому Users виступає ядром моделі даних.
     Таблиця TimeEntries розташована ліворуч на діаграмі та відповідає за зберігання відміток робочого часу. Вона має зовнішній ключ UserId, який пов’язаний з полем Id таблиці Users. У цій таблиці фіксуються тип події (EntryType), час початку (StartTime), час завершення (EndTime) та за потреби коментар (Comment). Таким чином реалізується відношення «один до багатьох»: один користувач може мати велику кількість відміток часу, що дозволяє детально відстежувати його робочий день.
     У нижній частині діаграми розміщена таблиця WorkSchedules, яка також пов’язана з Users через поле UserId. Вона описує робочий графік співробітника: час початку (StartWork) і завершення (EndWork) робочого дня, тривалість перерви (BreakMinutes) та робочі дні тижня (WorkingDaysMask). Наявність зовнішнього ключа дозволяє зберігати як загальний графік для всіх користувачів, так і індивідуальні графіки для конкретних працівників, що забезпечує гнучкість налаштувань.
     У верхній частині схеми знаходиться таблиця AbsenceRecords, яка зберігає інформацію про періоди відсутності співробітників: тип відсутності (Type), дату початку (DateStart), дату завершення (DateEnd) та коментар (Comment). Поле UserId пов’язує цей запис з конкретним користувачем у таблиці Users. Така структура дозволяє коректно враховувати відпустки, лікарняні та відрядження при формуванні звітів, не розглядаючи ці дні як порушення робочого графіка.
     Праворуч розташована таблиця AuditLogs, що реалізує журнал подій у системі. Вона містить зовнішній ключ UserId на таблицю Users і зберігає інформацію про виконані дії: назву дії (Action), назву сутності (EntityName), ідентифікатор запису (EntityId), час події (Timestamp), а також старі й нові значення (OldValue, NewValue). Це дозволяє відстежувати, хто і які зміни вносив у систему, що важливо для аудиту та забезпечення цілісності даних.
     Таким чином, діаграма структури БД демонструє чітко організовану модель, у центрі якої знаходиться таблиця Users, а всі інші таблиці — TimeEntries, WorkSchedules, AbsenceRecords та AuditLogs — пов’язані з нею через зовнішні ключі та описують різні аспекти робочої діяльності співробітників. Така схема забезпечує цілісність даних, логічність зв’язків і зручність подальшого розширення системи.

6 РОЗРОБИТИ ФУНКЦІЇ РОБОТИ З БД
6.1 Методи доступу до БД
     У даній системі доступ до бази даних реалізовано за допомогою набору функцій, кожна з яких відповідає за виконання конкретної SQL-операції над відповідною таблицею. Для кожної сутності було створено окремий модуль (клас), що містить методи роботи з таблицею та забезпечує виконання стандартних CRUD-операцій. Такий підхід дозволяє централізувати логіку взаємодії з базою даних та спрощує розширення системи в подальшому.
     Методи доступу до таблиці Users забезпечують створення нових користувачів, пошук за логіном або ідентифікатором, отримання повного списку співробітників та оновлення параметрів користувача. Окремі функції відповідають за активацію або деактивацію облікового запису. Дані операції використовують SQL-запити виду INSERT, SELECT, UPDATE та DELETE, а також перевірку унікальності логіну.
     Для таблиці TimeEntries розроблено функції, що дозволяють додавати нові відмітки робочого часу (початок/завершення роботи або перерви), отримувати записи за конкретний день чи співробітника, а також коригувати завершення події. Ці методи використовують параметризовані SQL-запити, що гарантує безпечне додавання інформації у базу та коректну роботу з часовими даними.
     Модуль роботи з таблицею WorkSchedules включає методи створення графіка, отримання персонального або глобального графіка для співробітника, його оновлення та видалення. Оскільки графік містить нормативні значення робочого часу, саме ці методи використовуються під час аналізу відповідності фактичних відміток встановленому режиму.
     Таблиця AbsenceRecords обслуговується окремим набором функцій, що дозволяють додавати періоди відсутності (відпустки, лікарняні, відрядження), отримувати записи за співробітником та фільтрувати їх за часовим діапазоном. Використання SQL-запитів дає змогу швидко формувати вибірки та враховувати ці дані під час генерації звітів.
     Для забезпечення прозорості роботи системи реалізовано методи роботи з таблицею AuditLogs. Функції цього модуля дозволяють додавати записи в журнал подій при створенні, зміні або видаленні об’єктів, а також зчитувати історію дій за конкретним користувачем або сутністю. Таким чином, таблиця AuditLogs забезпечує аудит змін та контроль за коректністю роботи системи.
     Усі методи доступу до БД виконують SQL-запити через єдиний механізм підключення до SQLite, що забезпечує узгодженість виконання операцій, а також спрощує тестування і подальшу підтримку програмної системи.
     

7 РОЗРОБКА API ДЛЯ СЕРВЕРНОЇ ЧАСТИНИ
7.1 Тип API, що буде використовуватися
     Для взаємодії між клієнтською частиною та сервером
використовується REST API. Дані передаються у форматі JSON
через стандартні HTTP-методи (GET, POST, PUT, DELETE, PATCH).
Авторизація користувачів здійснюється за допомогою JWT-токенів.
     Опис основних контролерів і ендпоінтів:

AuthController
Відповідає за реєстрацію та авторизацію користувачів.
     POST /api/auth/register — реєстрація нового
користувача (приймає UserRegistrationDto).
     POST /api/auth/login — вхід користувача, повертає
JWT-токен та коротку інформацію про користувача.
     GET /api/auth/me — отримати дані поточного
авторизованого користувача за переданим токеном.

UsersController
     Реалізує керування обліковими записами співробітників (тільки для адміністратора).
     GET /api/users — отримати список усіх користувачів.
     GET /api/users/{id} — отримати інформацію про
конкретного користувача.
     POST /api/users — створити нового користувача
(через UserCreateDto).
     PUT /api/users/{id} — оновити дані користувача
(ПІБ, роль, e-mail тощо).
     PATCH /api/users/{id}/deactivate — деактивувати
обліковий запис користувача.

TimeEntriesController
     Реалізує роботу з відмітками робочого часу.
     GET /api/time-entries/my?from=<date>&to=<date> — отримати
всі відмітки поточного користувача за вказаний період.
     GET /api/time-entries/user/{userId}?from=<date>&to=<date> —
отримати відмітки конкретного співробітника (для адміністратора).
     POST /api/time-entries/start-work — створити відмітку
початку робочого дня для поточного користувача.
     POST /api/time-entries/end-work — створити відмітку
завершення робочого дня (закриває останню незавершену зміну).
     POST /api/time-entries/break-start — відмітити
початок перерви.
     POST /api/time-entries/break-end — відмітити
завершення перерви.
     PUT /api/time-entries/{id} — виправити помилкову
відмітку (час або коментар) через TimeEntryUpdateDto.
     DELETE /api/time-entries/{id} — видалити відмітку
(доступно для адміністратора).

WorkSchedulesController
     Керує робочими графіками співробітників.
     GET /api/schedules/my — отримати актуальний графік
для поточного користувача.
     GET /api/schedules/{userId} — отримати графік
конкретного співробітника (для адміністратора).
     POST /api/schedules — створити новий графік
(через WorkScheduleDto) — глобальний або персональний.
     PUT /api/schedules/{id} — оновити параметри
існуючого графіка.
     DELETE /api/schedules/{id} — видалити графік.

AbsenceRecordsController
     Реалізує роботу з відсутностями (відпустки, лікарняні, відрядження).
     GET /api/absences/my — отримати всі записи
відсутності поточного користувача.
     GET /api/absences/user/{userId}?from=<date>&to=<date> —
переглянути відсутності обраного співробітника за період
(для адміністратора).
     POST /api/absences — створити новий запис відсутності
(через AbsenceCreateDto).
     PUT /api/absences/{id} — оновити дані про відсутність
(дати, тип, коментар).
     DELETE /api/absences/{id} — видалити запис
відсутності.

ReportsController
     Відповідає за формування аналітичних звітів щодо робочого часу.
     GET /api/reports/my/daily — отримати денний звіт
для поточного користувача.
     GET /api/reports/my/summary?from=<date>&to=<date> —
отримати узагальнений звіт за вибраний період.
     GET /api/reports/users/{userId}/summary?from=<date>&to=<date> —
зведений звіт по конкретному співробітнику (для адміністратора).
     GET /api/reports/summary?from=<date>&to=<date> —
загальний звіт по всіх співробітниках за період
(з можливістю фільтрації через ReportFiltersDto).
     GET /api/reports/export?format=<csv|xlsx>&from=<date>&to=<date> —
експорт звіту у файл для подальшої обробки.
     
AuditLogsController
     Відповідає за перегляд журналу подій і змін у системі (для адміністратора).
     GET /api/audit — отримати загальний список
записів журналу.
     GET /api/audit/user/{userId} — переглянути дії,
виконані конкретним користувачем.
     GET /api/audit/entity?name=<entityName>&id=<entityId> —
отримати історію змін певного запису (наприклад, відмітки
часу або користувача).
     Для передачі даних між клієнтом і сервером використовуються DTO-класи, що визначають структуру запитів і відповідей (UserRegistrationDto, UserDto, TimeEntryCreateDto, WorkScheduleDto, AbsenceCreateDto, ReportFiltersDto тощо). Це дозволяє уникнути передачі зайвої інформації, приховати внутрішню структуру таблиць та підвищити безпеку даних.

9 ПЕРЕВІРКА РОБОТИ СТВОРЕНОГО КОДУ
9.1 Тестування розроблених функцій
     У процесі перевірки роботи серверної частини системи було використано інтерактивну документацію Swagger UI. Через веб-інтерфейс Swagger здійснювалися тестові HTTP-запити до розроблених ендпоінтів, що дозволило перевірити коректність обробки вхідних даних, повернення відповідних кодів стану та структуру відповідей API.
     На рисунку 9.1 показано форму виклику методу реєстрації нового користувача. У блоці Request body задається JSON-об’єкт із полями fullName, login, email та password. У секції Responses відображено, що при коректних даних сервер повертає код 201 і об’єкт створеного користувача з полями id, fullName, login, email, role, isActive. Також передбачені відповіді 400 (помилка вхідних даних або вже існуючий логін) та 500 (помилка сервера або БД).
     

Рис. 9.1 – Тестування реєстрації користувача (POST /api/auth/register)

     На рисунку 9.2 наведено результат тестування ендпоінта для отримання інформації про поточного авторизованого користувача. Запит не містить тіла, а JWT-токен передається у заголовку Authorization: Bearer <token>. У відповідь сервер повертає код 200 і JSON-об’єкт із даними користувача. У випадку відсутності або некоректності токена повертається 401, а якщо користувача не знайдено — 404.
     

Рис. 9.2 – Отримання поточного користувача (GET /api/auth/me)

     На рисунку 9.3 продемонстровано тестування створення відмітки початку робочого дня. Ендпоінт не потребує параметрів у тілі запиту: час фіксується на стороні сервера для користувача, що викликає метод. У відповіді з кодом 201 повертається об’єкт відмітки з полями id, userId, entryType, startTime, endTime, comment. За відсутності авторизації сервер повертає код 401.
     

Рис. 9.3 – Створення відмітки початку робочого дня (POST /api/time-entries/start-work)

     На рисунку 9.4 показано тестування ендпоінта для отримання відміток робочого часу поточного користувача за період. У параметрах запиту передбачені опціональні поля from та to у форматі date-time, що дозволяють відфільтрувати записи за вказаним інтервалом. У разі успіху повертається код 200 та масив об’єктів відміток. Якщо запит виконується без дійсного JWT-токена, сервер відповідає кодом 401.
     

Рис. 9.4 – Отримання списку відміток поточного користувача (GET /api/time-entries/my)

     На рисунку 9.5 зображено екран Swagger для методу редагування існуючої відмітки часу. У шляху запиту задається параметр id — ідентифікатор запису, який редагується. У тілі запиту передається об’єкт з полями startTime, endTime та comment, причому можна змінювати одне чи кілька полів. У відповідь при успіху повертається оновлений запис з кодом 200. Якщо не передано жодного поля для оновлення, сервер повертає 400, якщо користувач не авторизований — 401, якщо намагається змінити чужу відмітку — 403, а при відсутності запису з таким id — 404.
     

Рис. 9.5 – Редагування відмітки робочого часу (PUT /api/time-entries/{id})

     На рисунку 9.6 продемонстровано тестування формування зведеного звіту за робочим часом поточного користувача. У параметрах запиту обов’язково задаються from та to у форматі date-time, які визначають період звіту. У разі успішного виконання повертається код 200 та об’єкт із полями userId, from, to, totalEntries, startCount, endCount, що відображають кількість відміток і окремо кількість початків та завершень робочого дня. Якщо один із параметрів не заданий, сервер повертає код 400, а при відсутності авторизації — 401.

	Рис. 9.6 – Формування зведеного звіту для поточного користувача (GET /api/reports/my/summary)

     На рисунку 9.7 показано тестування адміністративного ендпоінта для перегляду журналу аудиту системи. Запит підтримує опціональні параметри from та to для фільтрації записів за часом. У відповідь із кодом 200 повертається масив об’єктів з полями id, userId, action, entityName, entityId, timestamp, oldValue, newValue, що дозволяє простежити всі значимі зміни в системі. Якщо запит виконується без токена — повертається 401, а для користувача без прав адміністратора — код 403.

Рис. 9.7 – Перегляд журналу аудиту (GET /api/audit)
     Таким чином, за допомогою Swagger UI було проведено повне інтеграційне тестування основних функцій API: реєстрації та авторизації користувачів, фіксації й редагування відміток часу, роботи з відсутностями, формування звітів та перегляду журналу аудиту. Результати тестування підтвердили коректність реалізації розроблених ендпоінтів та їх відповідність описаній специфікації.
